## 8. What a game client needs from this server

What a desktop client could call today:

1. Is the server there: `GET /api/healthcheck?x=<unique>`. No auth. Answer `{ok, service, env, commit, ...}` (`api/healthcheck.ts:28-68`).
2. List designs: `GET /api/designs?email=<email>` or `?userId=<id>`. Answer `{designs:[...]}`, the 50 newest (`api/orders.ts:1326-1344`). Auth: the studio session cookie that the door hands out after its code form, or the landing hosts' admin sign-in cookie (`api/orders.ts:1569-1585`; `api/_lib/studioAccess.ts:32-52`; `server/accessGate.ts:82-131`). The cookie belongs to one environment and one host (`server/studioSession.ts:13-15`). There is no bearer token for this route.
3. Load one: `GET /api/designs/<number>`. Answer `{design:{id, userId, customerEmail, name, property, cart, status, createdAt, updatedAt}}` (`api/orders.ts:1309-1324`; `api/_db/schema.ts:645-657`). Same cookie. `property` is the whole design JSON.
4. Save: `POST /api/designs` with `{customerEmail or userId, name, property, cart?, status?}` gives 201; `PUT /api/designs/<number>` with the same body replaces it (`api/orders.ts:1356-1420`). Same cookie; an `Origin` header from another site is refused (`api/orders.ts:1571-1576`). A PUT that leaves out `name`, `cart` or `status` resets them (`api/orders.ts:1403-1408`). A POST with an email sends a "design saved" email (`api/orders.ts:1378-1383`). Previews refuse both (`api/orders.ts:1538-1541`).
5. What the server checks in a saved design: removed-wall indices, roof thickness, terrain cuts, boundary components, services, foundation, city, eco and engineering (`api/_lib/designSnapshotValidation.ts:37-59`). Everything else is stored as sent.
6. Several people in one design: `POST /api/shared-projects/live/join` with `{code, trade, avatar}` gives `{roomId, actorId, session, revision, model, players}`; then `sync` (`{revision, pose}`), `edit` (`{requestId, revision, changes[]}`) and `leave` with `Authorization: Bearer <session>` (`api/_lib/sharedBuild/handler.ts:46-48,141-283`; `src/sharedBuild/contract.ts:40-48,76-82`). No cookie is needed to join, and a request with no `Origin` header passes (`api/_lib/sharedBuild/handler.ts:115-124,131`; `api/_lib/studioAccess.ts:55-64`). Hosting a room needs the studio session (`api/_lib/sharedBuild/handler.ts:131-134`). This is the one route family a desktop client can use today with a token of its own.
7. List products: `GET /api/products?limit=100&offset=<n>`, with `category`, `search`, `slug`, `id` and more. No auth. Answer `{products:[...], total, limit, offset}` (`api/products.ts:213-234,1054-1063`). Sizes are in mm (`api/products.ts:77-79`).
8. Product ids inside a design: a placed item names its product by a bundled id, or by `m-<database id>` for a database row (`src/data/apiCatalogAdapter.ts:201`; `src/data/products.ts:41-47`). The bundled catalogue is compiled into the web bundle; no route serves it whole. The MCP tool `search_catalog` returns it 50 at a time with no offset (`api/_lib/designMcp.ts:277-297`).
9. Fetch a model file: `GET /models/<name>.glb`, a static file, open without the code (`server/studioPaths.ts:26`). The files are Draco-compressed with WebP textures (`scripts/optimize-models.mjs:9-13`), so the game's importer needs both.
10. Design tools without a browser: `POST /api/mcp` (section 3) and `GET /api/site/*` (section 2), both with no sign-in.

What is missing:

1. A sign-in a desktop client can hold. Saved designs open with a shared door cookie, not with a person's token (`api/orders.ts:1577-1585`). Clerk tokens exist only for shared spec projects and AI proposals (`api/_lib/sharedSpecs.ts:60-71`; `api/_lib/designAssistant.ts:226-246`).
2. An owner on a design, checked on the server (stage 2 adds it with the per-user sign-in).
3. A version on a design. The table has none (`api/_db/schema.ts:645-657`) and an update overwrites (`api/orders.ts:1401-1411`). The plan's rule "a save with an old version number is refused" has nothing to stand on yet. The live room already has one (`api/_lib/sharedBuild/handler.ts:272-281`).
4. A served catalogue and a served model table. The table from product to model (address, phone copy, facing, up axis) lives only in the web bundle (`src/data/productModels.ts:12,39`). The database has no model column (`api/_db/schema.ts:339-397`) and the product route carries none (`api/products.ts:71-92`).
5. The size rule on the server side. A body file has no fixed scale; the web app fits it to the product's sizes when it loads (`src/designer/fitToSize.ts:1-25`). The game needs the same rule, or files that are already at size.
6. One product id. The same product can appear under a bundled id and under `m-<id>`; the web joins them by SKU (`src/data/mergeCatalog.ts:20-33`; `src/data/productModels.ts:73-86`).
7. A link between a live room and a saved design. A room holds its own copy of the plan (`api/_db/liveBuildStore.ts:63-69`); nothing writes it back to the `designs` table.
8. A push channel. The live room is polled on a timer (`src/sharedBuild/client.ts:166-248`).
9. Cache headers for `/models/` (`vercel.json:86-91`), and an upload path for a model file (none found; the engine is a laptop tool, `docs/product-engine/README.md:97`).
10. Prices behind a check, and labour. The product route is open and carries the price (`api/products.ts:81,1054-1063`); the quote route adds up the caller's own prices (`api/cart-quote.ts:117-126`); no labour line exists on the server (grep).

## 9. Traps

1. The 12-function cap has no check in CI (`api/__tests__/paintCalcDispatch.test.ts:207-219`). 4. Prices on open surfaces today: the product route (`api/products.ts:81,1054-1063`), the open product page (`server/studioPaths.ts:27`; `src/pages/ProductDetailPage.tsx:115`), and the embed without `?pitch=1` (`src/demo/pitchEmbed.ts:17-30`).
